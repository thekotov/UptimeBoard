Rich Messages

Структурированные сообщения ботов: заголовки, таблицы, карты, коллажи, сноски и раскрывающиеся блоки — плюс потоковая генерация ответа, как в чат-ботах с ИИ. Собрано по официальным типам @grammyjs/types — то есть по тому, что Telegram реально отдаёт клиентам, а не по пересказу документации.

Контекст

Зачем это появилось

До Bot API 10.1 у бота было ровно два способа оформить текст: строка с parse_mode (HTML или MarkdownV2) или массив entities. Оба описывают линейный текст — жирный, ссылку, код. Ни один не умеет таблицу, карту или раскрывающийся блок.

Rich Messages добавляют второй, структурный слой поверх старого. Вместо строки с разметкой сообщение можно описать как дерево блоков — RichBlock: параграфы, заголовки, таблицы, цитаты, медиа, вложенные списки. Это тот же принцип, на котором строятся редакторы типа Notion — блоки, которые можно вкладывать друг в друга до 16 уровней.

Второе новое: sendRichMessageDraft и блок thinking. Они существуют для одного конкретного сценария — бота, который стримит ответ языковой модели токен за токеном и показывает пользователю индикатор «думаю». До 10.1 это приходилось имитировать частыми editMessageText; теперь под это есть отдельный, дешёвый по семантике механизм.

Форма данных

Два пути к одному сообщению

InputRichMessage принимает ровно одно из трёх полей: markdown, html или blocks. Первые два — текст с разметкой, где медиа подключается отдельным списком по идентификатору. Третье — готовое дерево объектов, где медиа лежит прямо внутри блока.

Правило одного поля. blocks, html и markdown взаимоисключающие — Telegram ожидает ровно одно из них в InputRichMessage. Смешать текстовую разметку с явным блоком в одном вызове нельзя.

Вложения

Как медиа попадает в сообщение

В текстовом режиме картинка не может лежать прямо в строке — синтаксис ![]() или <img> либо ссылается на прямой HTTPS-URL, либо на запись в media[] через псевдо-протокол tg://photo?id=/video?id=/audio?id=. Именно эта запись в media[] и умеет принимать файл на загрузку.

InputRichMessageMediamarkdown / html
// в тексте:  ![](tg://photo?id=uploaded1 "Подпись")

media: [{
  id: "uploaded1",        // 1–64 симв., A-Z a-z 0-9 _ -
  media: { type: "photo", media: new InputFile("photo.png") }
}]

Разница между режимами. В blocks медиа-объект (InputMediaPhoto и т.п.) лежит прямо внутри блока photo/video/… — без промежуточного id и без tg://-ссылки. Обходной путь через media[] нужен только текстовым режимам, потому что строка не может нести бинарные данные.

API

sendRichMessage, черновики и правки

sendRichMessage

Обычный отправляющий метод — работает в любом чате, где боту разрешено писать, принимает reply_markup, reply_parameters, message_effect_id, как и sendMessage. Разница только в одном параметре:

ПараметрТипЗаметка
chat_idnumber | stringкак у обычной отправки
rich_messageInputRichMessageобязательный, замена text
business_connection_idstring?отправка от имени Business-аккаунта
message_thread_idnumber?тема форума

sendRichMessageDraft — потоковая генерация

Только для приватных чатов. Каждый вызов с одним и тем же draft_id заменяет предыдущее превью у клиента — так строится эффект «печатает ответ». Превью существует не дольше ~30 секунд и никогда не становится настоящим сообщением само по себе.

editMessageText с rich_message

editMessageText принимает text или rich_message — можно превратить обычное сообщение в rich одним вызовом:

grammYApi.editMessageText
await api.editMessageText(chatId, messageId, {
  blocks: [
    { type: "heading", text: "Стало rich-сообщением", size: 3 },
  ],
});

Экосистема

Кто уже это поддерживает

На момент написания типизированную поддержку Rich Messages и Ephemeral Messages имеют только два фреймворка — оба обновились в течение нескольких дней после релиза Telegram.

БиблиотекаСтатусЕсли поддержки ещё нет
grammY (Node/TS) 10.1 + 10.2 —
aiogram 3.x (Python) 10.1 + 10.2 —
python-telegram-bot только до 10.0 bot.do_api_request(endpoint=…, api_kwargs=…)
Telegraf (Node) до 7.1 ctx.telegram.callApi("sendRichMessage", …)

Escape-hatch есть у всех четырёх: Bot API — обычный REST/JSON поверх HTTPS, так что вызов нового метода вручную через fetch/httpx работает независимо от того, знает ли о нём библиотека.

Из первых рук

Подводные камни

  • Ловушка Черновик не сохраняется сам

    Забыли отдельный вызов sendRichMessage после серии sendRichMessageDraft — пользователь увидел «печатает…», а в истории чата ничего не осталось.

  • Модель thinking — только для черновика

    Блок thinking валиден в sendRichMessageDraft, но не существует на стороне получателя — финальный sendRichMessage не должен его содержать.

  • Ловушка is_open и чекбоксы принимают только true

    is_open?: true, has_checkbox?: true, is_checked?: true — буквально литерал true, а не boolean. Чтобы выключить, поле просто не передают; false — ошибка типов.

  • Модель Ячейка таблицы обязана знать своё выравнивание

    align и valign у RichBlockTableCell не опциональны — их нужно указывать в каждой ячейке, даже когда подходит значение по умолчанию.

  • Модель Сноска — это два разных объекта

    reference (маркер в тексте) и reference_link (запись в подвале) — независимые типы, связанные только совпадением name/reference_name. Один без другого не рендерится как пара.

  • Ловушка Загрузка файла — не везде

    Прямая загрузка нового файла не поддерживается в черновиках (sendRichMessageDraft) и при редактировании инлайн-сообщений (editMessageText для inline_message_id). В обоих случаях годятся только file_id или HTTPS-ссылка.
